# SERA (Self-Evolving Medical RAG) Context & Roadmap

This document serves as a complete history, status update, and next-steps context window for SERA (Self-Evolving Medical RAG). You can feed this directly to any AI model context window to quickly align them with the codebase's current state.

---

## 1. Project Overview & Architecture
SERA is a self-evolving medical Assistant that combines standard RAG with automated knowledge synthesis, clustering, and continuous maintenance.

### Key Technology Stack
- **Backend**: FastAPI (Python) serving a REST API.
- **Vector DB**: ChromaDB with two primary collections:
  - `raw_chunks`: Raw snippets of parsed medical text (NHBLI, CDC, Cancer.gov, etc.)
  - `super_nodes`: Synthesized, high-level medical summaries generated by LLMs from raw clusters.
- **Relational DB**: SQLite (`data/sqlite/rag.db`) representing query logs, audit trails, and synthesis cluster queues.
- **Scheduler**: APScheduler running in the FastAPI lifespan to trigger pattern finding and maintenance.
- **Frontend**: HTML5, CSS3 (Vanilla), and ES6 JavaScript served at `/` via FastAPI's `StaticFiles`.

## 2. Status of Implementation (Phases 1 - 5)

### Phase 1: Ingestion & Baseline RAG
- Medical domain data ingested, parsed, and embedded in ChromaDB `raw_chunks`.
- A baseline retriever queried raw vectors and fed them to a generator to produce medical answers with citations.

### Phase 2 & 3: Logging & Clustering
- Every user query is logged in the SQLite `query_log` table.
- A background pattern finder runs periodically using APScheduler. It groups queries by semantic similarity into "clusters" in the `query_clusters` table.
- Concurrency protection ensures that cluster states (e.g. `synthesizing` locks) are managed cleanly.

### Phase 4: Summarizer Agent & LLM-as-Judge
- When a cluster's query count exceeds a threshold, an LLM summarizer generates a **super-node** summarizing all related raw chunks.
- The super-node is run through a strict verification engine ("LLM-as-Judge") checking for medical accuracy, hallucination, and alignment.
- Approved super-nodes are added to ChromaDB's `super_nodes` collection.

### Phase 5: Preferential Retrieval (Recently Completed)
- Rewrote `app/retrieval/retriever.py` to support dual-collection (super-nodes + raw chunks) retrieval.
- **SU4 ($\epsilon$-Greedy Score Booster)**: With probability $1-\epsilon$ (exploit, where $\epsilon=0.10$), super-node distances are boosted by a factor of $0.85$ to prefer consolidated knowledge. With probability $\epsilon$ (explore), no boost is applied.
- **SU5 (Hierarchical Masking)**: First pass queries super-nodes. Any parent meta-nodes found mask their children chunk IDs. The second pass (raw chunks) skips these children to prevent duplicate, redundant information in the context window.
- **SU10 (Atomic SQLite Access Logging)**: When a query is answered using super-nodes, their hits are logged immediately and atomically in SQLite `query_clusters` via an `IN` clause to prevent concurrent count discrepancies.
- **Bug Fix**: Standardised all retrieval keys to `"id"` (fixing a pre-existing silent bug where raw chunks returned `"chunk_id"` and were not resolved by the response mapper).
- **History Deletion**: Added a real-time `DELETE /query/` API endpoint to allow database-backed history wiping from the UI.

## 3. Frontend Architecture (`frontend/`)
The interface was refactored into two distinct pages:

### `home.html` (Landing & Chat Interface)
- Located at `/home.html` (with a FastAPI root redirect in `app/main.py` pointing `/` directly to `/home.html`).
- **Features**:
  - Clean search bar with smooth CSS micro-animations.
  - Floating glowing orbs and deep dark theme (`#0a0a0f`).
  - Interactive **History Sidebar** loaded from `sessionStorage` containing past queries.
  - **Real-Time Deletion**: Each history item contains a `✕` button. Clicking it prompts for confirmation, then removes the item locally and calls `DELETE /query/` on the backend to erase it from SQLite.

### `dashboard.html` (System Administration)
- **Features**:
  - Live system status checks polling `/health` with a pulsing dot.
  - Table of active clusters, synthesis statuses, and action logs.
  - Direct execution panels for forcing re-synthesis (`POST /admin/synthesize/{id}`).
  - Bias query simulation setup (biasing query ratio, poll intervals, stream progress).
  - Redundant chat interfaces removed to focus the page purely on system observability.

## 4. Next Phase Roadmap: Phase 6 (Maintenance, Decay & Hierarchy)
The next objective is to prevent database bloat, prune cold queries, and build hierarchical parent nodes (meta-nodes).

### 4.1 staleness_checker.py (SU8 - Soft-Staleness Check)
- **Problem**: Raw chunks get updated, but super-nodes still point to stale source chunks.
- **Goal**: Read super-node source chunk metadata and check if those raw chunks still exist/match in ChromaDB.
- **Logic**: If the match ratio is $< 1.0$, mark the super-node as `is_stale=True` but keep serving it. Simultaneously, flag the cluster in SQLite for async re-synthesis. Once re-synthesis finishes, swap the super-node and clear `is_stale`.

### 4.2 decay_scorer.py (SU3 & SU10 - Half-Life Decay)
- **Problem**: Unused super-nodes bloat ChromaDB.
- **Goal**: Apply exponential half-life decay to super-node scores based on access statistics.
- **Logic**: Sync SQLite `hit_count` (SU10) into ChromaDB metadata. If `days_since_last_access` exceeds threshold, prune the cold super-nodes.

### 4.3 hierarchy_merger.py (SU7 & SU11 - Hierarchy Merger)
- **Problem**: Super-nodes can become semantically close to each other, creating redundant higher-level summaries.
- **Goal**: Group highly-overlapping super-nodes into parent **meta-nodes** using an `in_hierarchy` lock flag (SU7) to prevent infinite loops, and apply ground-truth re-synthesis (SU11).

### 4.4 maintenance_job.py
- **Goal**: Bundle the three sub-systems into a periodic background APScheduler maintenance task.
